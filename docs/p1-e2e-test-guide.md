# FoodCafe P1 수동 E2E 테스트 가이드

문서 버전: 1.1  
작성 기준일: 2026-08-19  
대상: 현재 P1 구현분  
제외: 이메일 변경 운영 콜백 검증(ID 30)

## 1. 목적과 합격 기준

이 문서는 사용자가 브라우저에서 P1 기능을 직접 검증하기 위한 체크리스트다. 단순히 화면이 보이는지만 확인하지 않고 다음 네 가지를 함께 확인한다.

- 행동 직후 UI가 정확히 바뀌는가
- 새로고침 후에도 DB 상태가 유지되는가
- 비로그인·다른 사용자에게 비공개 정보가 노출되지 않는가
- 브라우저 콘솔 오류와 실패한 네트워크 요청이 없는가

P1 합격 조건은 다음과 같다.

- `필수` 테스트가 모두 통과한다.
- 테스트 중 예상하지 않은 HTTP 4xx/5xx 응답이 없다.
- 브라우저 콘솔에 새 오류가 없다.
- 좋아요·북마크·팔로우 수가 새로고침 전후 동일하다.
- 다른 사용자의 비공개 활동(좋아요·북마크 목록)이 공개 프로필에 나타나지 않는다.
- 이메일 변경 운영 검증은 이번 합격 판정에서 제외하고 별도 보류 항목으로 관리한다.

## 2. 검수 시작 전 준비

### 테스트 계정

계정 비밀번호나 인증 토큰은 문서에 기록하지 않는다.

- 계정 A: 테스트할 주 사용자
- 계정 B: A를 팔로우하고 A의 콘텐츠에 반응할 보조 사용자
- 비로그인 창: 시크릿 창 또는 별도 브라우저 프로필
- 선택 계정 C: 팔로우 목록의 `더 보기`를 검증할 때 사용

### 테스트 데이터

아래 데이터가 없으면 먼저 UI에서 생성한다.

- A가 작성한 게시글 1개 이상
- A가 작성한 레시피 2개 이상
- A가 작성한 레시피 조합 1개 이상
- B가 작성한 콘텐츠 1개 이상
- 최근 24시간 안에 생성한 좋아요·북마크·댓글·팔로우 활동

랭킹은 선택한 기간 안의 활동만 집계한다. 오래된 테스트 데이터만 있으면 화면이 정상이어도 빈 목록이 나올 수 있다.

### 실행과 기록

1. 프로젝트 루트에서 개발 서버를 실행한다.
   - `npm run dev`
2. `http://localhost:3000`을 연다.
3. Chrome 개발자 도구에서 `Console`과 `Network` 탭을 연다.
4. Network의 `Preserve log`를 켠다.
5. 각 테스트 전 현재 개수와 URL을 기록한다.
6. 실패 시 화면, Console, 실패 요청의 URL·상태 코드·응답 본문을 함께 캡처한다.

권장 결과 표기:

- `PASS`: 기대 결과와 일치
- `FAIL`: 기능 또는 데이터가 기대와 다름
- `BLOCKED`: 테스트 데이터나 외부 설정이 없어 실행 불가
- `N/A`: 이번 환경에서 의도적으로 제외

## 3. 공통 사전 점검

### P1-COMMON-01 주요 화면 응답

중요도: 필수

1. 홈, 레시피 목록, 게시글 목록, 통합검색, 랭킹, 공개 프로필을 차례로 연다.
2. 각 화면에서 로딩이 끝날 때까지 기다린다.
3. Network 탭에서 document 요청을 확인한다.

기대 결과:

- 각 문서 요청이 HTTP 200으로 끝난다.
- Next.js 오류 화면이나 빈 흰 화면이 나타나지 않는다.
- Console에 `Error`, hydration 오류, 무한 렌더링 오류가 없다.

### P1-COMMON-02 로그인 후 원래 위치 복귀

중요도: 필수

1. 비로그인 상태로 게시글 상세를 연다.
2. 좋아요를 누르고 로그인 모달을 연다.
3. 모달에서 로그인한다.

기대 결과:

- 홈으로 강제 이동하지 않는다.
- 로그인 전 게시글 상세 URL이 유지된다.
- 내비게이션의 로그인 버튼이 프로필 UI로 바뀐다.
- 로그인 직후 좋아요를 다시 누를 수 있다.

## 4. 게시글 좋아요(ID 06)

### P1-POST-LIKE-01 비로그인 접근

중요도: 필수

1. 비로그인 창에서 게시글 상세를 연다.
2. 좋아요 버튼을 누른다.

기대 결과:

- 좋아요 수가 먼저 바뀌지 않는다.
- 로그인 모달이 열린다.
- 모달을 닫으면 현재 게시글에 그대로 남는다.

### P1-POST-LIKE-02 토글과 영속성

중요도: 필수

1. A로 로그인해 좋아요 전 개수를 기록한다.
2. 좋아요를 한 번 누른다.
3. 버튼의 활성 상태와 증가한 개수를 확인한다.
4. 페이지를 새로고침한다.
5. 좋아요를 다시 눌러 취소하고 다시 새로고침한다.

기대 결과:

- 첫 클릭 후 활성 상태가 되고 개수가 정확히 1 증가한다.
- 새로고침 후 활성 상태와 개수가 유지된다.
- 취소 후 비활성 상태가 되고 개수가 정확히 1 감소한다.
- 빠르게 여러 번 눌러도 중복 좋아요나 음수 개수가 생기지 않는다.

### P1-POST-LIKE-03 마이페이지 연동

중요도: 필수

1. A가 B의 게시글에 좋아요를 누른다.
2. A의 마이페이지에서 게시글 활동 영역을 연다.
3. 좋아요 목록을 확인한다.
4. 원래 게시글에서 좋아요를 취소하고 목록을 다시 연다.

기대 결과:

- 좋아요를 누른 게시글만 A의 좋아요 목록에 나타난다.
- 취소 후 해당 게시글이 목록에서 사라진다.

## 5. 게시글 북마크(ID 07)

### P1-POST-BOOKMARK-01 비로그인 접근

중요도: 필수

1. 비로그인 창에서 게시글 상세의 북마크를 누른다.

기대 결과:

- 로그인 모달이 열리고 북마크 수는 바뀌지 않는다.
- 로그인 전 URL이 보존된다.

### P1-POST-BOOKMARK-02 토글과 영속성

중요도: 필수

1. A로 로그인해 북마크 전 개수를 기록한다.
2. 북마크를 누른 뒤 새로고침한다.
3. 다시 눌러 취소한 뒤 새로고침한다.

기대 결과:

- 등록 시 활성 상태와 개수가 새로고침 후에도 유지된다.
- 취소 시 비활성 상태와 원래 개수로 돌아온다.
- 빠른 중복 클릭에도 같은 사용자·게시글 조합이 한 건만 유지된다.

### P1-POST-BOOKMARK-03 마이페이지 연동

중요도: 필수

1. A가 B의 게시글을 북마크한다.
2. A의 마이페이지 게시글 북마크 목록을 확인한다.
3. 원래 게시글에서 북마크를 취소하고 목록을 다시 확인한다.

기대 결과:

- 등록한 게시글이 목록에 나타나고 취소하면 사라진다.
- B의 공개 프로필에서는 A의 북마크 활동이 노출되지 않는다.

## 6. 홈 인기·트렌드 집계(ID 08)

### P1-HOME-TREND-01 실데이터 링크

중요도: 필수

1. 홈의 `최근 7일 인기 레시피`, `커뮤니티 인기 이야기`, `지금 뜨는 레시피·조합`을 확인한다.
2. 각 영역의 첫 항목을 연다.

기대 결과:

- 화면에 표시된 제목·작성자·수치가 상세 화면의 실제 콘텐츠와 일치한다.
- 항목을 누르면 해당 리소스의 상세 URL로 이동한다.
- 임의의 고정 숫자나 반복된 가짜 콘텐츠가 나타나지 않는다.

### P1-HOME-TREND-02 빈 상태와 부분 장애

중요도: 권장

1. 최근 활동이 없는 기간 또는 테스트 데이터를 사용한다.
2. 홈을 연다.

기대 결과:

- 데이터가 없는 영역은 명확한 빈 상태를 표시한다.
- 한 집계 요청이 실패해도 관련 없는 홈 영역까지 모두 빈 데이터처럼 사라지지 않는 것이 목표 상태다.
- 실제 서버 오류를 `집계된 항목 없음`으로 오인하게 만드는 표현이 없어야 한다.

### P1-HOME-TREND-03 최근 활동 반영

중요도: 권장

1. 테스트 콘텐츠 하나를 정한다.
2. A와 B가 해당 콘텐츠에 좋아요·북마크·댓글 등 활동을 만든다.
3. 홈을 새로고침한다.

기대 결과:

- 집계 기간 안의 활동이 홈 수치 또는 순위에 반영된다.
- 새로고침할 때 순서가 이유 없이 뒤바뀌지 않는다.

## 7. 홈 카테고리 필터(ID 29)

### P1-HOME-CATEGORY-01 카테고리 연결

중요도: 필수

1. 홈에서 전체, 한식, 중식, 일식, 양식, 디저트, 샐러드, 간식, 다이어트를 각각 누른다.
2. 이동한 URL과 제목을 확인한다.
3. 목록의 모든 레시피 카테고리를 확인한다.

기대 결과:

- 전체는 `/recipes`로 이동한다.
- 나머지는 `/recipes?category=<영문 키>` 형태로 이동한다.
- 제목에 선택한 카테고리가 표시된다.
- 선택한 카테고리 범위 밖의 레시피가 섞이지 않는다.
- 간식에는 프로젝트 정의상 `간식`과 `분식`이 함께 포함될 수 있다.

### P1-HOME-CATEGORY-02 검색·페이지 이동과 필터 유지

중요도: 필수

1. 카테고리를 선택한다.
2. 검색을 실행한다.
3. 결과가 여러 페이지라면 다음 페이지로 이동한다.

기대 결과:

- 검색 및 페이지 이동 후에도 `category` 쿼리가 유지된다.
- 페이지를 이동해도 다른 카테고리 데이터가 섞이지 않는다.

## 8. 일·주·월 랭킹(ID 09)

### P1-RANK-01 기간과 종류 전환

중요도: 필수

1. `/ranking`을 연다.
2. 일간·주간·월간을 차례로 누른다.
3. 각 기간에서 레시피와 레시피 조합을 전환한다.

기대 결과:

- URL에 `period=day|week|month`와 `type=recipe|combo`가 정확히 반영된다.
- 기간을 바꿔도 선택한 종류가 유지되고, 종류를 바꿔도 선택한 기간이 유지된다.
- 한 번에 최대 50개만 표시된다.
- 항목 클릭 시 올바른 상세 화면으로 이동한다.

### P1-RANK-02 순위 우선순위

중요도: 필수

테스트 데이터로 동점 상황을 만들 수 있을 때 수행한다.

1. 같은 기간 안에서 트렌드 점수가 다른 콘텐츠를 준비한다.
2. 점수가 같다면 고유 참여자 수가 다른 콘텐츠를 준비한다.
3. 두 값이 같다면 최근 북마크 수가 다른 콘텐츠를 준비한다.
4. 화면 순서를 확인한다.

기대 결과:

- 트렌드 점수 내림차순
- 동점이면 고유 참여자 수 내림차순
- 다시 동점이면 최근 북마크 수 내림차순
- 모두 같으면 ID 오름차순으로 고정되어 새로고침해도 순서가 흔들리지 않는다.

### P1-RANK-03 기간 경계

중요도: 권장

1. 24시간, 7일, 30일 경계 안팎의 활동이 있는 데이터를 준비한다.
2. 일간·주간·월간 결과를 비교한다.

기대 결과:

- 기간 밖의 활동이 해당 기간 점수에 포함되지 않는다.
- 콘텐츠의 누적 수치와 기간 내 수치가 혼동되지 않는다.

## 9. 통합검색 정렬(ID 11)

### P1-SEARCH-01 공통 정렬

중요도: 필수

1. 레시피·조합·게시글에 모두 존재하는 검색어를 입력한다.
2. 최신순, 좋아요순, 조회순을 차례로 선택한다.
3. 각 콘텐츠 영역의 순서를 확인한다.

기대 결과:

- 최신순은 각 리소스의 생성 시간 기준 내림차순이다.
- 좋아요순은 각 리소스의 좋아요 수 기준 내림차순이다.
- 조회순은 각 리소스의 조회 수 기준 내림차순이다.
- 정렬 변경 시 URL의 `sort`가 바뀌고 각 영역 페이지 번호는 1로 초기화된다.

### P1-SEARCH-02 보기 방식과 페이지 상태

중요도: 필수

1. 검색 결과를 목록 보기로 바꾼다.
2. 레시피·조합·게시글 중 한 영역의 다음 페이지로 이동한다.
3. 정렬을 변경한다.

기대 결과:

- URL의 `view=list`가 유지된다.
- 한 영역의 페이지 이동이 다른 영역의 페이지 번호를 임의로 변경하지 않는다.
- 정렬 변경 시 모든 결과 영역이 새 정렬의 첫 페이지로 돌아간다.

### P1-SEARCH-03 빈 검색과 특수문자

중요도: 권장

1. 빈 검색어, `%`, `_`, 따옴표가 포함된 검색어를 각각 시도한다.

기대 결과:

- 화면이나 SQL 요청이 깨지지 않는다.
- 예상하지 않은 전체 데이터 노출이나 500 오류가 없다.
- 결과가 없으면 정상적인 빈 상태가 표시된다.

## 10. 프로필 정렬·공개 범위(ID 10)

### P1-PROFILE-01 자기 프로필 정규화

중요도: 필수

1. A로 로그인한다.
2. 주소창에 A 자신의 `/profile/<A_ID>`를 직접 입력한다.

기대 결과:

- `/profile`로 이동한다.
- 내 활동 탭과 편집 기능은 마이페이지에서만 제공된다.

### P1-PROFILE-02 타 사용자 공개 범위

중요도: 필수

1. A로 로그인하거나 비로그인 상태에서 B의 공개 프로필을 연다.
2. 레시피와 레시피 조합 영역을 확인한다.
3. 주소창에 `tab=bookmark`, `tab=like`, `section=post`를 각각 직접 넣어본다.

기대 결과:

- B가 작성한 레시피와 조합만 공개된다.
- B의 좋아요·북마크·게시글 활동 탭은 나타나지 않는다.
- 비공개 파라미터는 `tab=written`과 허용된 섹션으로 정규화된다.
- 비공개 데이터가 HTML 응답이나 Network 응답에 포함되지 않는다.

### P1-PROFILE-03 정렬·검색·보기 방식

중요도: 필수

1. B의 공개 프로필에서 인기순과 최신순을 전환한다.
2. 검색어를 입력한다.
3. 보기 방식을 전환하고 페이지가 있다면 다음 페이지로 이동한다.

기대 결과:

- 인기순 URL은 `sort=like`, 최신순은 `sort=recent`다.
- 검색·정렬·보기 방식이 URL에 유지된다.
- 검색 또는 섹션 변경 시 잘못된 페이지 번호로 빈 화면이 남지 않는다.

### P1-PROFILE-04 공개 정보 최소화

중요도: 필수

1. 비로그인 창에서 B의 공개 프로필을 연다.
2. 화면과 HTML 응답에 표시되는 사용자 정보를 확인한다.

기대 결과:

- 공개에 필요한 이름, 프로필 사진, 팔로우 수만 노출한다.
- 이메일, 역할, 관리자 여부, 로그인 시각 등 계정 정보는 노출되지 않아야 한다.

## 11. 팔로우(ID 13)

### P1-FOLLOW-01 비로그인 접근

중요도: 필수

1. 비로그인 창에서 B의 공개 프로필을 연다.
2. 팔로우 버튼을 누른다.

기대 결과:

- 팔로워 수가 먼저 변하지 않는다.
- 로그인 모달이 열린다.
- 로그인 후 B의 공개 프로필로 돌아온다.

### P1-FOLLOW-02 토글·개수·영속성

중요도: 필수

1. A로 B의 공개 프로필을 연다.
2. 팔로워 수를 기록하고 팔로우한다.
3. 새로고침한 뒤 버튼과 수를 확인한다.
4. 언팔로우하고 다시 새로고침한다.

기대 결과:

- 팔로우 시 버튼이 `언팔로우`로 바뀌고 B의 팔로워 수만 1 증가한다.
- B의 팔로잉 수는 바뀌지 않는다.
- 새로고침 후 상태와 수가 유지된다.
- 언팔로우 시 정확히 원래 상태로 돌아온다.
- 빠른 중복 클릭에도 관계가 중복 생성되지 않는다.

### P1-FOLLOW-03 팔로워·팔로잉 목록

중요도: 필수

1. B 프로필의 팔로워 수를 누른다.
2. 목록의 사용자 이름과 이미지를 확인한다.
3. 목록의 사용자를 눌러 해당 프로필로 이동한다.
4. 팔로잉 수도 같은 방식으로 확인한다.

기대 결과:

- 모달에 공개 정보만 표시된다.
- 수치와 목록 총원이 일치한다.
- 빈 목록은 정상적인 빈 상태를 보여준다.
- 20명을 넘는 경우 `더 보기`가 중복 없이 다음 항목을 붙인다.
- 사용자 선택 시 모달이 닫히고 올바른 공개 프로필로 이동한다.

### P1-FOLLOW-04 프로필 연속 이동 회귀

중요도: 필수

1. B의 팔로우 목록에서 C의 프로필로 이동한다.
2. C의 팔로워 수와 팔로우 상태를 확인한다.
3. 브라우저 뒤로 가기로 B에 돌아온다.

기대 결과:

- B의 로컬 상태가 C의 프로필에 남지 않는다.
- 각 프로필의 팔로워 수와 버튼 상태가 해당 사용자 기준으로 표시된다.

### P1-FOLLOW-05 자기 자신 팔로우 차단

중요도: 필수

1. A의 마이페이지와 `/profile/<A_ID>`를 확인한다.

기대 결과:

- 자기 자신을 팔로우하는 버튼이나 성공 경로가 없다.
- 직접 API를 호출하더라도 자기 팔로우는 400 계열로 거부된다.

## 12. 현재 검수에서 확인된 이슈 상태

자동 검증은 코드와 개발 서버 기준 결과다. 로그인 상태 전환처럼 실제 브라우저 세션이 필요한 항목은 위 수동 E2E 절차로 최종 확인한다.

### RESOLVED-P1-01 공개 프로필 이메일 노출

- 공개 데이터 원본을 `public.profiles`로 분리했다.
- 공개 필드는 ID, 이름, 사진, 생성·수정 시각, 팔로워·팔로잉 수로 제한했다.
- 이메일과 역할·관리자 여부·로그인 시각은 공개 프로필과 사용자 목록 API에서 제외했다.

### RESOLVED-P1-02 사용자 목록 API의 존재하지 않는 DB 객체 참조

- 사용자 조회 코드는 실제 원본인 `public.profiles`를 사용한다.
- `/api/users?limit=50&page=1`의 HTTP 200과 공개 필드 제한을 확인했다.
- 사용자 저장소의 우회 타입 단언을 제거하고 생성 타입을 `profiles` 기준으로 갱신했다.

### FIXED-PENDING-E2E-P1-03 Supabase Auth 클라이언트 중복 경고

- 브라우저 인증 클라이언트는 모듈 단일 인스턴스로 만들고 `AuthProvider`가 하위 인증 UI에 전달한다.
- 서버 사전 렌더링에서는 브라우저 클라이언트를 프로세스 전역에 저장하지 않는다.
- 홈·공개 프로필·랭킹·사용자 API 요청 중 서버 로그에서 중복 경고가 재현되지 않았다.
- 로그인·로그아웃 직후 내비게이션 상태 변경은 `P1-COMMON-02`에서 브라우저 콘솔과 함께 최종 확인한다.

### RESOLVED-P1-04 홈 집계 오류의 빈 상태 위장

- 홈의 다섯 집계 요청을 서로 독립적으로 처리한다.
- 실패한 영역은 오류 안내를, 성공했지만 결과가 없는 영역은 빈 상태 안내를 표시한다.
- 일부 순위 데이터만 실패하면 정상 결과는 유지하고 부분 장애 안내를 함께 표시한다.

### KNOWN-P1-05 공개 프로필의 1개짜리 내부 탭

- 공개 프로필은 비공개 활동 탭을 숨겼지만 내부에 `작성 레시피` 또는 `작성 조합` 탭 하나만 남는다.
- 선택지가 하나뿐인 탭은 상호작용 의미가 없으므로 제목으로 바꾸거나 내부 탭 자체를 숨기는 편이 명확하다.

## 15. 선택 DB 무결성 확인

UI 테스트가 끝난 뒤 Supabase SQL Editor에서 읽기 전용으로 확인할 수 있다. 결과가 모두 0이어야 한다.

```sql
select count(*) as self_follow_rows
from public.user_follows
where follower_id = following_id;

select count(*) as duplicate_follow_pairs
from (
  select follower_id, following_id
  from public.user_follows
  group by follower_id, following_id
  having count(*) > 1
) duplicated;

select count(*) as duplicate_post_like_pairs
from (
  select user_id, post_id
  from public.post_likes
  group by user_id, post_id
  having count(*) > 1
) duplicated;

select count(*) as duplicate_post_bookmark_pairs
from (
  select user_id, post_id
  from public.post_bookmarks
  group by user_id, post_id
  having count(*) > 1
) duplicated;
```
